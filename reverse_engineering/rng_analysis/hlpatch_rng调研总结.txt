============================================================
hlpatch RNG/PRNG 调研总结（证据校正版）
修订日期：2026-07-18
============================================================

【结论摘要】

当前能够采集客户端观测到的 RNG 相关状态转移，并将其与动作、回合和实际结果
关联。当前证据不足以从该状态直接计算未来训练结果，也不足以断言客户端不存在
PRNG、服务器预计算整局训练结果，或状态字差等于随机调用次数。

============================================================
1. 已实现且可保留的能力
============================================================

hlpatch SO：
- 从 WorkSingleModeData 相关对象的 offset 0x198 读取四个 u32。
- 记录训练前后完整 before/after 四元组。
- 保存 Hook sequence、raw sub_id、回合、剧本、干劲、失败率、结果和毫秒时间。
- 使用加锁有界队列供 Hook 写入和 HTTP 读取。
- /summary 输出 rng_state，并可附带最新 rng_transition。
- s1_numeric_delta 明确只是原始数值变化特征，不是 PRNG 调用次数。

uma-juece：
- 按 sequence 去重和关联 RNG transition。
- 将状态、动作、实际属性变化写入育成局 JSON 并进入持久上传队列。

这些能力用于“观测与验证”，不等于已经获得确定性预测器。

============================================================
2. FixedTurnCharaSeed：同名属性必须区分类
============================================================

CONFIRMED：

- Gallop.WorkSingleModeData 有 get_FixedTurnCharaSeed()；现有方法转储仅将返回类型
  粗分为 ptr，准确类型尚未恢复。
- 训练备份系统另有返回 i4 的同名 getter：
  - TrainingBackupDataScenarioOnsenAssistantCommand
  - ITrainingBackupData
  - TrainingBackupDataDefault

因此不能把所有 FixedTurnCharaSeed 都解释为同一个 [u32;4] 结构。
当前 offset 0x198 的四元组应标记为 observed rng_state，直到运行时反射确认：

- 字段准确名称；
- 字段类型；
- getter 返回类型；
- offset；
- 字段所属游戏版本。

============================================================
3. 客户端比赛随机系统
============================================================

CONFIRMED：

- StandaloneSimulator.IRaceRandomGenerator 有四个 GetRandom 重载：
  int/float 返回，各有一参数和二参数版本。
- 存在具体类 StandaloneSimulator.RaceRandom，具有对应四个重载。
- 存在 SingleModeRaceRandomProgram HTTP Model 和 MessagePack Formatter 名称。
- ObscuredIdleSingleModeEndInfo 有 RaceRandomProgramArray getter/setter。

结论：客户端比赛模拟侧存在具体随机实现候选，旧结论“客户端零 RNG 计算”错误。

仍未知：

- RaceRandom 是否正式实现该接口（需接口映射确认）；
- 它是本地算法，还是按游标读取服务器下发程序；
- SingleModeRaceRandomProgram 的字段和元素类型；
- 比赛随机系统是否与育成训练使用同一随机流。

比赛侧的证据不能直接推广为训练结果预测。

============================================================
4. 服务器与未来结果
============================================================

联网育成的最终状态由服务器响应确认，但当前材料没有证明：

- 育成开始时已预计算全部72回合训练、事件和彩圈；
- RaceRandomProgramArray 包含训练未来结果；
- offset 0x198 四元组足以独立决定所有结果；
- 点击训练之前客户端已经持有该动作的实际结果。

最值得验证的问题是：服务器响应或客户端内存中是否在点击前已经存在可直接解析的
未来信息。如果存在，应解析 payload；如果不存在，继续做状态转移统计建模。

============================================================
5. 明确禁止的解释
============================================================

- 不把 rng_state 称为服务器原始 seed 或完整服务器 PRNG 状态。
- 不猜测它必然是 Xorshift128、Xoshiro128、PCG 或 MT。
- 不把 s1_after-s1_before 称为消费步数。
- 不建立“种子越大越好”的规则。
- 不用精确 seed 查表直接接受/拒绝育成局。
- 不把 single_mode_program.random_group_id 当训练 RNG 参数。
- 不因 metadata 出现 _seedArray 就断言训练使用 System.Random。

_seedArray/_inext/_inextp 属于典型 System.Random 运行库邻域；只有找到训练业务调用链
后才能讨论其相关性。s_seed 也必须先确认所属类型。

============================================================
6. MDB 的正确用途
============================================================

- single_mode_chara_program：角色与育成比赛赛程组配置。
- single_mode_program：比赛实例、月份、资格、奖励和少量随机赛程组配置。
- random_group_id：1118行中仅12行非零，是特殊赛程随机组线索。

MDB 可用于解释赛程和比赛 program，但不能直接解码四元组或计算训练失败、彩圈和
育成事件结果。

============================================================
7. 当前正确路线
============================================================

第一阶段（结构恢复）：
1. 运行时反射 WorkSingleModeData 的字段类型与 getter 真实返回类型。
2. 恢复 SingleModeRaceRandomProgram 字段和 formatter 顺序。
3. 恢复 RaceRandom 字段、构造器、接口映射和调用方。

第二阶段（手机小样本验证）：
- 同回合重复读取状态，确认稳定性；
- 比较 summary、Hook before/after 和下一回合状态；
- 覆盖训练、休息、外出、比赛；
- 对齐请求/响应、sequence、turn 和实际属性变化。

第三阶段（按证据分流）：
- 若点击前已有未来结果：解析服务器下发数据；
- 若没有：用上下文 + observed rng_state + 动作做统计模型；
- 若仅比赛有 random program：比赛解析和训练建模分开处理。

CI 绿色只证明编译。手机完成上述验证前，不将 RNG 数据正式投入模型训练。
