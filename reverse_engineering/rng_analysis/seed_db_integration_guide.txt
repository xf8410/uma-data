种子数据库集成指南 — 已废弃草案
状态：DO NOT IMPLEMENT
修订日期：2026-07-18
================================================================================

一、废弃原因
================================================================================

旧版指南建议把客户端读取值直接作为“种子”，建立精确 seed→结果映射，并据此执行
育成局 ACCEPT/REJECT/SAMPLE。该设计建立在以下未验证假设上：

1. offset 0x198 的四元组就是完整服务器 PRNG 状态；
2. 相同四元组在不同上下文中必然产生相同未来结果；
3. 已知该值即可确定性预测训练结果；
4. 状态字差可表示随机调用次数；
5. 客户端已经掌握生成未来结果所需的全部隐藏输入。

这些假设目前均未得到字段类型、调用链、真实网络 payload 或手机实验支持。因此旧版
数据库 schema、Rust 示例、HTTP 端点以及自动 SL 决策流程不得直接集成。

二、当前可安全保存的数据
================================================================================

若需要数据库，只能将其设计为“观测数据集”，而不是“已解码种子数据库”。每条记录
至少保存：

- session_id
- scenario_id / scenario
- chara_id
- turn
- hook sequence
- timestamp_ms
- raw_sub_id（原始观测，不冒充已验证 CommandId）
- observed rng_state before/after（完整四元组）
- s1_numeric_delta（原始特征；不是 PRNG 调用次数）
- changed_mask
- motivation
- failure_rate
- action 与 action source
- 实际训练结果
- 实际属性、体力、技能Pt变化
- 客户端/SO版本与二进制 commit/hash
- 数据验证状态

去重键应至少结合 session_id 与 hook sequence；不能仅按四元组去重。

三、当前禁止实现
================================================================================

在第一阶段证据完成前，不实现：

- /seed/decision 的 ACCEPT/REJECT 自动决策；
- “高价值种子”精确查表；
- 根据四元组大小排序；
- 根据 s1 差值估算消费步数；
- 自动放弃育成局；
- 把比赛 RaceRandomProgramArray 推广为整局训练随机序列；
- 以当前数据进行确定性 SL 过滤。

四、重新启用的最低证据门槛
================================================================================

只有满足以下条件，才能另行设计预测数据库：

1. 运行时反射确认目标字段的准确名称、类型和 offset；
2. 明确状态所属随机流及更新时机；
3. 恢复算法或确认服务器下发了可直接解析的未来程序/结果；
4. 用多局手机实验验证同状态、同上下文、同动作的可重复性；
5. 排除 sequence 重置、跨局串联和 Hook 时序错配；
6. schema 明确区分 observed、inferred、confirmed 字段。

五、当前替代方案
================================================================================

继续使用现有采集链路：

hlpatch：采集完整状态转移与 Hook 上下文。
uma-juece：按 sequence 去重，关联回合、动作和实际属性变化，持久化上传。
uma-data：保存原始育成局 JSON，用于后续统计和验证。

模型只能学习“观测状态与上下文下，不同决策对应的统计结果”，不得宣称已经恢复服务器
PRNG 或能从状态字直接计算随机步数。

原指南中的生成式示例和未实现函数均已移除，避免被误认为可执行方案。
