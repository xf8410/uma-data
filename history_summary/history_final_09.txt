错误条目 6：统计数字冲突
------------------------------------------------------------
报告 A/B 中出现的互相冲突的数字：
  hlpatch 提交数：170 / 约85 / 88
  CI Runs：100 / 121
  Release：20 / 31

冲突原因：
  - git log --all 把多个 ref 的重复/分叉历史算入
  - force-push 后旧 ref、remote-tracking 分支并存
  - API per_page=100 只是分页大小，不是总数
  - Release 条目数 vs Release 资产行数混淆（v3.24.3-libil2cpp 有 3 个 asset 但算 1 个 Release）
  - 统计范围有的从 7月7日，有的包含更早日期

建议统一口径：
  - 提交数：git rev-list --count --since=... --until=... origin/main
  - Actions：GitHub API total_count + 分页去重 run ID
  - Release：按唯一 release ID/tag 计数，不按 asset 行数
  - 在重新统一前，不把"170提交、16失败、20/31 Release"列入已确认事实

错误条目 7：data/docs 不触发 CI
------------------------------------------------------------
报告 B 原文：
  "data/docs 类不触发 CI"

问题：错误
  - 当前 workflow 配置：on: push: branches: [main]，没有 paths 或 paths-ignore
  - 任何 main push 都触发 CI
  - 直接证据：7fbf0ec docs 提交 → Actions #420 → success → v3.24.16 SO 附件重新上传

正确表述：
  - data/docs 提交会触发 CI 和 Release 附件覆盖
  - 这本身是 workflow 配置问题，应加 paths-ignore

2.2 DataCollector 问题判断基本成立（源码可直接确认）
------------------------------------------------------------
以下问题可以通过阅读源码直接确认，不需要运行时证据：

  1. 动作是回合推进后事后推断，不是点击时直接记录
  2. 训练收益全0时，余弦匹配会因 predMag < 1 跳过
  3. /summary 错误 JSON 没有 stats，parseSnapshot() 会失败
  4. 异步上传线程重新读取可变的 sessionId/scenario/turns.size()
  5. 回合重置和 final 上传成功都可能调用 startNewSession()
  6. App 只恢复 sessionId/turn_count，没有恢复实际的 turns/prevSnapshot/scenario
  7. 每回合独立线程执行 GitHub GET/PUT，存在旧 SHA 导致 409 的风险
  8. 已有文件名与内部 session_id 不一致，属于直接的数据损坏证据

这些可以作为后续修复依据。

------------------------------------------------------------
3.1 当前最可信的故障链
------------------------------------------------------------

故障链 A（/summary 崩溃 → 数据丢失）：
  hlpatch /summary 在 get_SingleMode 之后发生 native SIGSEGV
  → App 收到 cooldown/error 而不是完整 stats
  → DataCollector 丢失快照
  → 后续拿非相邻回合做事后动作推断
  → action Unknown 或误判

故障链 B（App 采集 Bug，独立于 A）：
  异步上传使用变化后的 sessionId/scenario
  + 重复 startNewSession
  + 不完整恢复
  + 并发 GitHub PUT
  → 文件名错位、跨局混合、回合残缺

故障链 C（数据语义 Bug，独立于 A/B）：
  shining/heads 的 -1/null/0 没有统一语义
  + gains 经常全0
  + 动作不是直接 CommandId 真值
  → 数据不适合直接训练

================================================================================
一、用户需求
================================================================================

用户有一个赛马娘辅助项目（uma-helper / uma-juece），需要在无 root 的
Android 设备上，建立「游戏进程 ↔ 辅助 App」的通信通道，用于获取游戏内
实时数据（育成回合、赛事信息、剧情选项等）并在悬浮窗中显示。

用户提供了以下参考资料：
1. https://github.com/xf8410/uma-juece — 用户自己的项目
2. https://hachimi.noccu.art/zh-cn/hachimi — Hachimi 项目文档
3. https://github.com/EtherealAO/Hachimi-Edge — Hachimi-Edge 项目
4. winhttp.dll 逆向分析报告（已上传）— Hachimi PC 端完整逆向报告

================================================================================
二、背景调研结果
================================================================================

【Hachimi 架构】
- PC 端：winhttp.dll 代理注入，IPC 端口 4693（tiny_http + JSON）
- Android 端：Zygisk 注入（需要 root/Magisk/KernelSU）
- IL2CPP Hook：63 个赛马娘专属 Hook 点（Gallop.* 命名空间）
- 导出了完整的 Plugin API，支持第三方 .so 插件
- 有 IPC 机制：enable_ipc / ipc_listen_all / ipv4_only 等配置项

【Carrotless 项目（关键发现）】
- 地址：https://github.com/LeadRDRK/Carrotless
- 作者：LeadRDRK（与 Hachimi 同一作者）
- 功能：无 Zygisk、无 root 注入赛马娘 Android 客户端
- 原理：代理 Unity 的 libmain.so 入口，Hook 注入 + 转发原始调用
- 最新版本：v0.2.3（2024年2月）
- 配套工具：UmaPatcher（一键改包+签名+安装）

【winhttp.dll 分析报告要点】
- 63 个 IL2CPP Hook 点，类名跨平台通用
- Plugin API：il2cpp_get_field_value / il2cpp_runtime_invoke 等
- IPC 设计：tiny_http + JSON 通信模式
- SQLite 查询语句可直接用于查询游戏数据
- 渲染 Hook：IDXGISwapChain::Present + WndProc
- 音频 Hook：CriAtomExAcb/CriAtomSourceBase

三、方案对比
================================================================================

共分析了 6 种方案：
