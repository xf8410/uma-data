一、项目定位
================================================================================

Hachimi 是赛马娘(Umamusume)PC客户端的社区Mod注入器。winhttp.dll 是其核心组件，
通过 Windows DLL 代理机制（替换系统 winhttp.dll）注入到游戏进程中，实现：

1. IL2CPP 运行时 Hook（读取/修改游戏内存数据）
2. 翻译系统（UI翻译 + 剧情自动翻译）
3. 游戏内覆盖层 GUI（基于 egui 的配置编辑器）
4. 资源替换与修改
5. IPC 进程间通信（端口 4693）

================================================================================
第一章：插件基础架构确立
================================================================================

一、端口18765和18766的由来
──────────────────────────────────

【问题】插件（游戏进程内）和浮窗App之间需要通信，怎么通信？

【决策过程】
1. Hachimi框架的插件API（hachimi_init_v3）允许插件注册自己的逻辑
2. 插件用Rust的tiny_http库在游戏进程内启动HTTP Server
3. 端口选择18765：随意选的高位端口，避免冲突；如果被占用就换
4. 浮窗App（uma-juece）同样启动HTTP Server在18766端口
5. 两个端口都是127.0.0.1本地回环，不暴露到外网，安全性OK

【确认方式】
- 手机浏览器访问 http://127.0.0.1:18765/health → 返回 {"status":"ok"} 证明插件HTTP服务正常
- 手机浏览器访问 http://127.0.0.1:18766/health → 同样验证App服务正常
- 两个端口互不冲突，各自独立运行

二、推送架构演进
──────────────────────────────────

【v1.0 轮询时代】
- App每2秒向插件18765端口发GET请求拉数据
- 问题：轮询间隔固定，数据更新不及时；空轮询浪费CPU

【v1.7 推送重构】
- 插件端加后台线程，每1秒读一次游戏内存
- 生成summary hash比对，只有数据变化时才POST到App 18766端口
- App端完全移除轮询代码，改为被动接收推送
- 新增配置文件 /data/local/tmp/uma_hook_config.json 允许用户自定义推送地址和间隔

【推送线程闪退问题】
- 原因：推送线程在游戏进程内，大量调用il2cpp_runtime_invoke（~130次/周期）
  从非游戏主线程调用会导致SIGSEGV崩溃
- 治疗过程见第二章

【兜底轮询】
- App端加5秒兜底：如果5秒内没收到推送，自动每2秒向18765/summary拉取
- 防止推送链路断连导致浮窗卡死在"等待数据"

================================================================================
第二章：闪退问题全记录
================================================================================

一、ObscuredInt加密的发现
──────────────────────────────────

【问题】读取角色属性时，所有字段都返回奇怪的大数字（如444444）

【排查过程】
1. 用 /fields 端点dump出WorkSingleModeCharaData的字段列表
2. 发现 _speed、_stamina、_hp、_motivation 等字段类型全是 ObscuredInt
3. ObscuredInt是Cygames的反作弊加密：存储的是加密后的key，不是真实值
4. 直接读内存拿到的是key（444444），必须调C# getter方法（如get_Speed()）才能解密

【解决方案】v3.7.0
- 改用 il2cpp_runtime_invoke 调用C# getter方法，让游戏自己解密
- 代价：每次读取都要走il2cpp_runtime_invoke，性能开销大但数据正确

二、il2cpp_runtime_invoke累积崩溃
──────────────────────────────────

【问题】访问 /summary 或 /training/predict 端点时游戏闪退
        拉面杯（scenario 14）剧本下必崩

【排查过程】v3.22.14 → v3.22.18
1. v3.22.14：跳过拉面杯的getter调用 → 还在step47崩溃（"got ramen_ds"）
2. v3.22.15：彻底跳过read_training_predict的ramen段 → 还在step47崩溃
3. v3.22.16：跳过read_summary_inner的ramen段 → 更严重，闪退到桌面
4. 加step日志追踪：发现崩溃点不在ramen段，而在buffs段

【根因确认】
- read_summary_inner() 到达buffs段前已累积约130次il2cpp_runtime_invoke调用
- 从非游戏主线程大量调用il2cpp_runtime_invoke导致SIGSEGV崩溃
- /debug/rameninfo 单独调用4次il2cpp_runtime_invoke不崩，因为次数少

【调用统计】
  Phase 1 (stats读取)     = 16次
  Phase 1b (skills读取)   = ~31次
  Phase 2 (training读取)  = ~81次
  Phase 3-5 (支援卡等)     = 0-4次
  到达buffs段前总计        = ~128-131次
